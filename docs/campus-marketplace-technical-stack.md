# 校园二手与代拿小程序全栈技术方案

版本 v0.1 · 设计稿 · 2026-11-17

需求基线 [校园二手与代拿微信小程序需求 v0.3](campus-marketplace-requirements.md)

## 1. 架构与服务职责

我按单校区全量使用设计首版，涵盖学生证人工审核、二手发布与预约、快递代拿、外卖代拿、校外代购、站内通知和运营后台。通过认证的学生用同一账号发单与抢单，权限按校区和具体记录校验。线下结算沿用需求约定，系统保存预约与履约状态。

我把校园业务作为独立项目部署，沿用 TaskFlow 的 Java 版本和服务边界约定。每个业务服务拥有独立 schema、数据库账号、迁移脚本和可执行 JAR，可以单独发版与扩容。服务通过版本化 HTTP 或事件交互，应用模块之间无 Maven 依赖。跨业务查询通过 API 组合。服务内部按业务能力组织 `controller`、`service`、`service/impl`、`mapper`，由控制器调用服务接口。

| 服务 | 负责范围及权威数据 |
| --- | --- |
| `campus-gateway` | 对外路由、入口认证、限流、请求标识；仅持有路由和限流配置 |
| `campus-identity` | 微信登录、会话撤销、账号与校区权限、学号和学生证人工审核、认证审计 |
| `campus-market` | 商品、预约、成交、帖子审核与二手交易争议 |
| `campus-errand` | 三类代拿任务、抢单、履约、超时、帖子审核与代拿争议 |
| `campus-notification` | 站内通知、未读状态、事件消费去重记录 |

~~~text
小程序 → HTTPS 负载均衡 → Nginx → Gateway → 对应业务服务
运营端 → HTTPS 运营入口 → Nginx 提供静态页面
                              └→ Gateway 运营路由 → 对应业务服务
业务服务 → 自有 MySQL schema、Redis 查询缓存、按权限访问对象存储
业务服务 Outbox → 内网事件 API → 通知服务
~~~

## 3. 防超卖与订单幂等

我把一条代拿任务、一件二手商品分别视为单份资源。数据库主库的事务决定资源归属，Redis 用于缓存和削峰。成功响应在事务提交后返回。

### 3.1 代拿任务只允许一笔接单

1. 客户端为一次操作生成 `Idempotency-Key`，网络异常时沿用原键。服务端校验会话与抢单资格，再在本地事务内用唯一键 `(actor_id, action, request_key)` 登记请求及参数摘要。相同请求返回已提交的业务结果，同键异参返回冲突。提前限流或回滚的请求可沿用原键重试。
2. 按任务主键取得行锁，再执行以下条件更新。截止时间由取得行锁后的数据库语句判断，避免临近截止的请求在等锁时过期却仍成功。

   ~~~sql
   UPDATE errand_task
   SET status = 'CLAIMED', claimed_by = :actorId, claimed_at = UTC_TIMESTAMP(6)
   WHERE id = :taskId
     AND campus_id = :campusId
     AND publisher_id <> :actorId
     AND status = 'OPEN'
     AND deadline_at > UTC_TIMESTAMP(6);
   ~~~

3. 更新一行后，在同一事务中写接单记录、幂等结果和 Outbox。给 `errand_claim.task_id` 加唯一约束。任何写入失败都回滚。更新零行时根据当前状态返回已被接单、已取消或已过期；同一接单者重复提交可以取回已有记录。
4. 待抢单撤销与到期扫描竞争同一任务行，按当前状态和截止条件写入。已接单后的取消、履约超时或争议保留原接单记录。需要重新发布时创建新任务 ID。

### 3.2 二手商品同一时间只有一个有效预约

1. 发起预约时按商品主键加锁，校验商品已公开在售、买家身份和校区。同一事务创建预约快照、把商品设为待卖家处理，并写入 `active_item_reservation`。该表以 `item_id` 为主键，`reservation_id` 加唯一约束。
2. 待卖家处理、已预留、待买家确认，以及仍未处理完的争议均保留占用。拒绝、撤回、符合条件的取消或超时在同一事务内结束预约、移除占用并恢复在售。成交时同步更新商品为已成交并释放占用，保留预约历史。
3. 接受、取消、到期、下架和成交统一按商品行、预约行的顺序加锁。释放时同时核对当前预约 ID 和起始状态，防止旧预约的取消或超时操作误释放新预约。

订单事务只访问本服务 MySQL，外部 HTTP、文件操作、通知投递和缓存失效均在事务外执行。连接中断导致提交结果未知时，向主库查询原幂等键。尚未读到结果时只允许用同一键重试，由唯一键处理仍在提交的事务。死锁或锁等待超时后先回滚，再有限重试。网关关闭 POST 自动重放。主库故障切换时先隔离旧主库，确认新主库包含已确认的订单提交后恢复写入。无法确认时暂停抢单和预约，恢复并对账后开放。 [InnoDB 语句加锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html) · [MySQL 主键与唯一约束](https://dev.mysql.com/doc/refman/8.4/en/constraint-primary-key.html)

## 4. 全校并发与容量规划

我用 **3 万可用账号、峰时 2,000 名活跃用户**作首轮假设。每名活跃用户平均每秒产生 0.3 次 API 请求，对应 **600 RPS**，图片流量单独统计。混合负载先按 90% 查询、10% 写入运行 30 分钟，再用 **1,200 RPS 持续 5 分钟**测突发，另测**一秒内 1,000 个请求竞争同一资源**。学校规模和试点流量确定后调整压测模型及实例规格。

| 场景 | 设计与故障处理 |
| --- | --- |
| 午饭与放学集中访问 | 给大厅和二手列表按校区、公开状态、类型和排序字段建联合索引，用发布时间与 ID 做稳定游标，限制页大小和筛选组合。首版使用受限的 MySQL 标题检索，按中文检索效果与慢查询评估搜索组件。 |
| 热门列表频繁回源 | 热门首屏采用 cache-aside，TTL 初值 15–30 秒，加随机抖动并合并同键回源。业务提交后失效相关键，失效失败由 Outbox 重试。列表允许短暂陈旧，抢单与预约结果读取主库。 |
| 瞬间涌入同一任务 | 网关按账号和任务 ID 限流，业务服务给订单写入保留独立并发额度。过载返回 `429` 或 `503`，客户端退避并沿用请求键。 |
| Redis 不可用 | 启用每实例限额和受控回源，保留主库连接给关键订单写入和必要查询，限制高成本搜索。数据库约束继续生效。 |
| 实例及连接扩容 | 网关和关键 API 首轮以至少两个跨主机实例为起点。按 p95、线程、连接池等待及行锁等待调规格。所有实例连接池上限之和按数据库容量预算配置，为迁移、监控和恢复留余量。 |
| 到期和通知积压 | 按 `(status, deadline_at, id)` 分批查候选，逐条条件更新。Outbox 以短事务认领，按租约回收，事务外投递；通知服务以事件 ID 去重。失败退避重试，达到上限时告警并支持人工重放。 |

## 5. 数据安全

| 数据或入口 | 设计 |
| --- | --- |
| 微信身份 | 小程序将临时登录 code 交给身份服务。身份服务通过 HTTPS 调用 `code2Session`，以 `(appid, openid)` 定位账号，签发短时业务令牌。AppSecret 与微信会话密钥仅在服务端使用，登录 code、密钥和原始令牌均从日志中排除。 |
| 校区权限与撤销 | 网关及服务验证业务令牌签名、签发方、受众及过期时间。每次受保护请求由身份服务按用户主键核对当前校区、账号权限和会话状态，列表鉴权在读取缓存之前完成。权限查询走索引、设置短超时，并纳入混合负载压测。无法核验时拒绝访问。 |
| 学生证照片 | 微信登录后仅本人可提交；认证服务校验文件实际格式、大小和尺寸，重编码去除 EXIF，写入启用服务端加密的私有 COS。认证预览逐次校验申请归属或审核权限，经服务端流式响应，设置 `Cache-Control: no-store`。证件照片只进入人工认证链路。 |
| 学号与私密履约字段 | 学号、取件码和取餐凭证以 AES-GCM 加密，数据密钥交由 KMS 管理，列表默认掩码。订单接口校验当事人和当前状态，取消或终态后关闭普通读取。站内通知仅携带记录 ID 与必要状态。 |
| 运营权限与审计 | 独立运营会话使用多因素认证、安全 Cookie 和 CSRF 防护。校园审核、内容审核、争议处理分别授权。查看证件、审核、封禁和争议处置记录操作人、目标、时间和结果。服务间使用 TLS 与独立服务身份。 |
| 备份与清理 | MySQL 加密备份和时间点恢复，生产和测试环境隔离。为证件、学号、取件凭证和审计记录分别配置留存期，提供删除与注销流程，恢复数据后补跑删除任务。具体期限在提审前确认。服务与数据库凭据存入密钥管理设施。 |
| 图文与发布 | 普通帖子图文接入微信内容检测，失败时保留待审核供运营处理。帖子图使用签名访问，CDN 先鉴权再返回缓存。SQL 使用参数绑定；测试、压测及提审使用虚构认证材料，构建流水线扫描依赖和镜像漏洞。 |

业务服务通过身份 API 获取用户标识、认证状态和校区。完整学号和证件原图留在身份服务的数据边界。 [Spring Security JWT 验签与受众校验](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html)

## 6. 交付与验收

1. 打通入口、微信登录、上传学生证、人工审核、驳回重提与准入，交付小程序及后台基础界面。
2. 完成二手预约与成交，以及三类代拿发布、抢单与履约。先验证数据库多连接竞争，再接入至少两个 API 实例做压测。
3. 完成图文审核、通知、纠纷、告警、数据清理与恢复演练，准备真机体验版和微信提审。

| 验收项 | 方法与目标 |
| --- | --- |
| 并发正确性 | Testcontainers 用真实 InnoDB 模拟多会话竞争，查询最终记录验证任务仅一笔接单、商品仅一笔有效预约。多实例热点测试要求同一资源只有一个成功结果，其余响应为合法冲突或限流。 |
| 事务和幂等 | 覆盖抢单与撤单、抢单与到期、预约与下架、旧预约取消与新预约竞争。模拟提交后响应丢失，原键重试返回原结果。重复投递一次业务事件，只生成一条对应站内通知。 |
| 混合吞吐 | k6 以固定到达速率运行，核对实际 RPS 与掉落迭代。600 RPS 首轮目标为列表 p95 ≤ 250 ms，抢单和预约 p95 ≤ 500 ms，非预期错误率 < 0.5%。1,200 RPS 首轮目标为列表 p95 ≤ 500 ms，抢单和预约 p95 ≤ 1 s，非预期错误率 < 1%。混合负载把限流计入未满足请求，合法状态冲突单独统计。 |
| 数据安全 | 验证未认证、跨校区、非当事人和撤销权限用户访问 API、分享链接及私有文件时的权限控制。审核员访问生成审计。检查日志和缓存中的敏感字段暴露。 |
| 故障恢复 | 演练 Redis 停止、API 重启、Outbox 重投和 MySQL 切换，验证旧库失去写入权，已确认订单可以对账。记录实际恢复用时和数据恢复点，据此定 RTO 与 RPO。 |
| 真机与后台 | iOS、Android 真机走通登录、上传、审核后准入、发单、抢单和交付。运营后台验证人工审核、举报和争议流程。 |

验收记录使用明确日期、数据规模、环境、命令、实际 RPS、延迟分位数、错误分类、锁等待和数据库最终结果。当前容量与时延数字为首轮目标，需通过压测和预生产演练确认。 [k6 固定到达速率](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/) · [k6 阈值](https://grafana.com/docs/k6/latest/using-k6/thresholds/)
